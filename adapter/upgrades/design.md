# 上游升级控制层设计

已有 M01–M10 回答“一个功能在一个平台怎样实现和认证”。本控制层回答“切换 Dynamo 与厂商引擎后，哪些适配必须迁移、哪些证据失效、怎样形成可以回退的发布候选”。顶层目标是保留已有适配行为并纳入上游变化，而非要求每次新版本重新实现全部模块。

| 阶段 | 输入与自动工作 | 完成条件 / 阻塞 |
| --- | --- | --- |
| U00 冻结 | 固定 B/H/T 完整 SHA、实际 Git merge-base、计划、旧 stack 和功能契约 | 干净的源码工作区、目标 SHA 与官方审查记录一致 |
| U01 影响分析 | 比较 B→H 和 B→T；映射 implementation_paths、公共依赖、功能前后依赖 | 无法分类的路径保守扩大回归，绝不默认无影响 |
| U02 迁移台账 | 每个本地改动路径生成稳定 AD 编号；列出上游变更、新能力待审项 | 所有项在最终候选 SHA 上有处理理由，无 blocked |
| U03 候选隔离 | 收集实际镜像 receipt，创建拥有者可核对的 worktree，合并固定 T | 原 HEYI 不移动；冲突保留；人工/AI 完成迁移并提交 |
| U04 本地检查 | 冻结的 argv 检查、有界超时、逐次日志与 SHA | 当前候选检查成功，日志未改变，检查没有修改源码 |
| U05 功能回归 | 输出 site scope/命令，接入已有 doctor、任务编译、AI loop、独立验证器 | 逐平台 M01–M10 当前输入验收通过；不能漏 case |
| U06 配对回归 | 旧 HEYI / 新 HEYI / 新原生，规范化指标与原始哈希，对齐比较条件 | 正确性通过且在冻结的回归预算内；原生失败单独诊断 |
| U07 M10 交付 | 复用 build/dependencies/export/verify_archive/import/smoke/seal | 新镜像、部署文件、离线包与现场 smoke 属于同一身份 |
| U08 发布提案 | 再审计各平台 feature evidence，复查交付字节和回退方案 | 生成只读提案；实际合并、打标签、推送与上线另行执行 |

执行顺序允许 U02/U03 交错：通常需要先看到真实冲突才能确定 rewrite 或 upstream_replaced。U02 的最终审查必须指向已经提交的候选，不能提前把设想当结论。检查或适配失败后保留该 attempt，后续成功不抹去历史。

`lock.json` 以内容哈希固定输入；`analysis.json` 每次从固定 Git 对象重新计算并对照，修改文件不能缩小范围；`state.json` 指向最新记录，`events.jsonl` 保留过程。使用文件锁避免两个控制器并发修改会话。模型结果只是建议，release 使用现有确定性证据门禁。哈希可发现意外改写，但不是针对拥有任意文件写权限者的防篡改安全边界。

版本身份有三个层次：计划中的目标标签和版本、已下载镜像观察到的 RepoDigest/包版本、候选中生效的 canonical stack。只有第三层进入 M01–M10 campaign；第一层不会修改当前已验证配置。运行镜像探测时使用 inspect 得到的 image ID、禁止隐式 pull，不挂载设备、不使用宿主网络。

一个平台的引擎更新，即使 Dynamo 的文件路径不变，也会使原来的运行证据失效。未知上游目录、Python/Rust/构建/契约公共改动采取保守全范围回归。当前 any-of 的影响分析同时考虑所有备选依赖；执行时必须由现场 scope 选定实际路径。未来可增加更细的符号索引，但它只能辅助解释风险，不能仅因 Git 无冲突而减少现有回归要求。

本次默认吞吐下限为旧版本的 90%，TTFT/TPOT p95 上限为旧版本的 110%。这是首版回归告警预算，可在 init 前审查调整，不是生产 SLA。旧/新 HEYI 同时更换引擎时，差异归因于整个软件栈；新 HEYI 对新原生的比较只能在相同模型、资源和负载口径下解释，不能许诺 Dynamo 必然带来增益。

人工与 AI 都使用相同 CLI 和会话文件。AI 在现有 bounded harness 中实施功能，身份、预算、资源清理和独立断言继续由原工作流约束。真实 Codex/Claude/GPT 账户调用并未在本次重新验收，不能把 CPU fixture 宣称为模型自主升级成功。
